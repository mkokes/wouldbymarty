# Agent Development Guide

Context for any AI coding agent working in this repo. See `README.md` for setup, the Instagram token and deployment secrets.

## Project Overview

WouldByMarty is a single-page landing site for a custom woodworking shop. It's populated with posts from the @wouldbymarty Instagram account, and it's an installable PWA hosted on **GitHub Pages**. It's a single npm package at the repo root: a Vite + React 19 + TypeScript 7 SPA.

The site used to be an e-commerce storefront (Next.js, Convex, Clerk, Stripe, MSW mocks, Expo mobile scaffold, `packages/ui`). All of that was removed from `main`. It's preserved on the `ecommerce-archive` branch and the `ecommerce-v0` tag. Restore from there rather than rebuilding if the shop comes back.

## Project Layout

```
.github/workflows/deploy.yml   GitHub Pages workflow (checks, build, deploy)
.husky/pre-push                lint + tests before every push
index.html                     page shell, meta tags, inline theme script
public/                        manifest, service worker, icons, static images
scripts/fetch-instagram.mjs    build-time Instagram sync (posts, media, token refresh)
scripts/prerender.mjs          build-time SSR into dist/index.html
src/App.tsx                    the landing page
src/components/                Hero, FeaturedPost, InstagramGrid, About, Picture, ThemeToggle
src/lib/                       Instagram feed, site copy, theme, scroll reveal
src/test/                      Vitest setup and fixtures
```

`src/data/instagram.json` and `public/instagram/` are generated by the sync and git-ignored.

## Commands

From the repo root:

```bash
npm install
npm run build          # Instagram sync + tsc + vite build + pre-render -> dist/
npm test               # vitest
npm run typecheck      # tsc --noEmit (TypeScript 7 / native compiler)
npm run lint           # oxlint
npm run format         # oxfmt (write); format:check to verify
npm run dev            # Vite dev server on :5173
npm run preview        # serve dist/; use it to test the service worker
npm run test:watch     # Vitest in watch mode
```

A husky `pre-push` hook (`.husky/pre-push`) runs `npm run lint` and `npm test`. `npm install` installs it through the `prepare` script. The workflow sets `HUSKY=0` and runs lint, format check, tests and build, in that order. Keep all of them green.

## Tooling

- **Vite 8** with `@vitejs/plugin-react`. Vitest is configured in the same `vite.config.ts` (jsdom environment, `src/test/setup.ts` loads jest-dom matchers and RTL cleanup).
- **oxlint** (`.oxlintrc.json`): correctness rules are errors, suspicious rules are warnings. The react, typescript, import, jsx-a11y and vitest plugins are enabled. `react-in-jsx-scope` is off because the project uses the automatic JSX runtime.
- **oxfmt** (`.oxfmtrc.json`): single quotes, 120-column lines. It also formats the Markdown and JSON files at the root, so run `npm run format` after editing docs rather than hand-formatting.
- Tests sit next to the source as `*.test.ts(x)`. Components take data as props (e.g. `App` receives `feed`), so they can be tested without the generated JSON.

## Architecture

### Static, pre-rendered SPA: there is no server at runtime

GitHub Pages serves the files in `dist/`. `index.html` holds the meta, Open Graph, manifest and icon tags, plus an `<!--app-html-->` placeholder inside `#root`.

- After `vite build`, `scripts/prerender.mjs` does an SSR build of `src/entry-server.tsx` with Vite's API (into a temporary `dist-ssr/`). It calls `render()` (`renderToString`) and writes the HTML into the placeholder in `dist/index.html`.
- `src/main.tsx` hydrates when `#root` already has markup (production), and otherwise does a client render (the dev server). It also registers the service worker in production.
- Rendering must be deterministic between the build and the browser, or hydration will mismatch. `entry-server.test.tsx` hydrates the server HTML and fails on recoverable errors. The footer year uses `suppressHydrationWarning`, because a build can straddle New Year.

### Instagram data is fetched at build time

- `scripts/fetch-instagram.mjs` runs as `predev`/`prebuild`. It loads `.env.local` via `node --env-file-if-exists`.
  - It calls `graph.instagram.com` for the profile and the latest 14 posts. It also pages through older posts to find the hero post (`HERO_SHORTCODE` in the script).
  - It stores the media in `public/instagram/`, because Instagram CDN URLs are signed and expire and the static page must not hotlink them. Images go through sharp into WebP renditions (`POST_WIDTHS` / `POSTER_WIDTHS` / `AVATAR_WIDTHS`), each with a tiny base64 blur placeholder. The hero reel's MP4 is downloaded as-is, up to 30 MB.
  - It writes `src/data/instagram.json`. Both outputs are git-ignored.
  - It never fails the build. On an error it keeps the previous data, or writes an empty feed.
  - In GitHub Actions with `GH_SECRETS_TOKEN` set, it refreshes the 60-day Instagram token, masks it in the logs, and saves it back to the `INSTAGRAM_ACCESS_TOKEN` repository secret with `gh secret set`. The value is passed on stdin. The workflow's `GITHUB_TOKEN` can't write secrets, hence the separate fine-grained PAT.
- `src/lib/instagram.ts` pulls the JSON in through an eager `import.meta.glob`. That resolves to `{}` when the file is missing, so a missing file isn't an error. `normalizeFeed()` fills in the defaults.
- Freshness comes from a scheduled GitHub Actions run (daily), not from runtime fetching.

### PWA

- `public/manifest.webmanifest` holds the manifest, and the icons are in `public/icons/`.
- `public/sw.js` is a hand-written service worker:
  - Navigations are network-first, with an offline fallback to the cached `/`.
  - Vite's hashed `/assets/*` files are cache-first.
  - Video requests (range requests) bypass the worker so the hero reel can stream.
  - Other same-origin assets are stale-while-revalidate, with the runtime cache capped at 60 entries.
  - Bump `VERSION` when you change caching behaviour.

### Other

- `src/lib/site.ts` holds the handle, profile URL, tagline, fallback bio, and the drafted "About the maker" copy.
- Page layout (`App.tsx`):
  - **Hero:** muted looping video, with a poster and a pause button. It doesn't autoplay with reduced motion or Save-Data.
  - **Featured post:** `arrangePosts()` picks the newest post that isn't the hero. Its caption's first line becomes the headline, and trailing hashtags are stripped by `cleanCaption()`.
  - **Grid:** up to 12 tiles, trimmed to whole rows of three. On two-column mobile, CSS hides a lone last tile.
  - **About** section.
- `Picture` renders responsive images that fade in over the blurred placeholder.
- Dates use a fixed locale and UTC (`formatPostDate`) so the pre-rendered HTML matches hydration.
- **Theme:** there's a 3-way toggle (system/light/dark) in `src/lib/theme.ts` + `ThemeToggle`, stored in `localStorage` (`wbm-theme`) and applied as `data-theme` on `<html>`.
  - An inline script in `index.html` applies the stored theme and adds the `js` class before first paint. Keep its key and colors in sync with `theme.ts`.
  - The toggle uses `useSyncExternalStore` with a "system" server snapshot, so pre-rendering doesn't cause hydration errors.
- **Scroll reveal:** elements with `data-reveal` fade in through `src/lib/reveal.ts`, which is initialised in an effect after hydration. They're only hidden under `html.js` with no reduced-motion preference.
- Styling is plain CSS classes in `src/styles.css`, built on CSS custom properties.
  - The "warm workshop" palette is cream and oak. The dark theme is walnut, and it's defined twice: under `prefers-color-scheme: dark` (unless `data-theme="light"`) and under `[data-theme="dark"]`.
  - Fonts are loaded in `index.html`: Chango for the wordmark, Fraunces for headings, Montserrat for body text.
  - A fixed SVG-noise overlay adds the grain.

### Deployment

`.github/workflows/deploy.yml` runs on pull requests (checks and build only), on pushes to `main`, on a daily schedule and on manual dispatch.

- A push to `main` deploys only when the commit belongs to a merged PR. A `gate` step checks this with `gh api repos/…/commits/<sha>/pulls`, so direct pushes never go live.
- Merges are detected from the push rather than the PR `closed` event, because the `github-pages` environment only allows `main`.
- Scheduled and manual runs always deploy, which is how new Instagram posts reach the site.
- The custom domain `wouldbymarty.com` is configured in the repo's Pages settings, not with a CNAME file.

Repository secrets (Settings → Secrets and variables → Actions):

| Secret                   | Value                                                         |
| ------------------------ | ------------------------------------------------------------- |
| `INSTAGRAM_ACCESS_TOKEN` | Long-lived Instagram token (see README)                       |
| `GH_SECRETS_TOKEN`       | Fine-grained PAT for this repo with "Secrets: Read and write" |
